专有云内部复制脚本可能同时涉及数据复制和平台元数据切换。阅读脚本时，需要把“代码具备某个动作”和“项目执行了该动作”分开。

## 技术在哪些项目用到

项目 H 的问题记录描述了 OTS 全量与增量迁移的阶段完成情况，并保存了一个内部复制工具目录，内含 Python 脚本、配置和平台控制命令。

目录名指向 OTS，但样例配置的实例名和部分帮助文案指向 ODPS。仅凭目录名不能认定该样例就是现场 OTS 实例的实际配置。

## 项目背景

工具源码包含实例查询、目标建表、复制启动、复制状态检查、访问开关和实例归属更新等动作。这些能力依赖专有云内部接口与运维权限，不等同于公网 TableStore 的通用迁移 API。

## 实施步骤

以下顺序来自源码结构的整理，没有在原环境重新执行：

1. **确认工具适用环境。** 核对产品、平台版本、内部接口及运行依赖。源码使用 Python 2 风格，不能假设 Python 3 可以直接运行。
2. **确认源目标身份和实例范围。** 配置文件包含平台地址、AG 节点和复制 endpoint；需要确认实例的真实归属及目标集群。
3. **枚举表与表组。** 源码区分表组、子表和独立表，范围核对必须覆盖这些对象。
4. **读取复制状态。** 对照工具输出中的复制模式、完成标记和时间戳，而不是只看一个汇总值。
5. **创建目标对象并启动复制。** 具体步骤依赖内部协议；此处只描述流程，不提供可直接执行的平台变更命令。
6. **检查全量与增量。** 源码定义了检查点和复制状态判断，需要结合日志确认失败、重试和是否真正追平。
7. **建立写入边界。** 工具包含停止、启用及实例切换动作，这些操作会影响平台访问或归属，执行顺序必须由对应版本运维方案确定。
8. **补齐业务验证。** 建议对表范围、读取结果、写入可用性和应用访问做独立验证。

## 问题与解决方法

### RPO 指标含义不清

源码以复制完成标记和时间戳计算一个延迟值，不能单凭字段名称断言它测量了所有业务数据丢失风险。现场记录的零 RPO 应理解为当时工具或报告的阶段观测，仍需一致性和业务验证。

### 样例与产品命名不一致

应回到运行配置、日志、实例信息和平台版本确认工具实际用途，不能将 OTS 目录中的每个参数直接写成通用 OTS 迁移步骤。

### 内部操作与通用迁移方法混用

平台级开关与实例归属更新具有特定语义。复用时应采用相应版本支持的运维方案，并明确失败恢复方法；本文没有执行任何内部操作。

## 经验与结果边界

原记录没有描述 OTS 故障，工具源码也不证明现场完成了某次切换。本篇是工具能力和证据边界的分析，阶段结果仅引用原问题记录。
