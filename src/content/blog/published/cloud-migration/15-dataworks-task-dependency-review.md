大量业务 SQL 被导出到目录后，很容易被当成重复文档。实际上，代码、任务配置、依赖关系和运行环境可能分别存放，迁移验收必须将它们重新关联。

## 技术在哪些项目用到

项目 H 归档了 DataWorks 任务导出材料，包含 SQL、Shell、JSON 形式的任务配置和文本依赖文件。目录同时包含多个项目空间或环境，以及重复导出副本。这里的文件数量不能直接当作生产任务数量。

## 项目背景

样本 `.cdp` 是可解码的 JSON，包含 `baseId`、`configuration`、`projectId`、`tenantId`、`type`、`version` 等字段；`.virtual` 样本则是文本，不能仅因扩展名陌生而排除。

原问题记录还指出，部分节点没有数据源配置，源端在迁移后继续新增或修改任务。这说明任务导出不等于目标调度可运行。

## 实施步骤

1. **按内容识别文本。** 除 TXT 和 Markdown，还要识别 SQL、脚本、JSON、配置文件及任务导出文本。
2. **按环境和项目空间分类。** 避免把测试环境与生产环境、源端与目标端副本合并为一套任务。
3. **分别提取代码和配置。** 关联任务 ID、代码、版本、环境、数据源与依赖信息。
4. **对原文件做内容去重。** 相同哈希只表示字节相同；业务任务去重还要考虑项目、环境和标识，不能删除不同环境中的合法副本。
5. **检查调度拓扑。** 建议核对孤立节点、缺失依赖、循环依赖和跨项目依赖，确认目标调度规则与原环境一致。
6. **适配数据源与身份。** 租户、项目、用户和连接信息属于环境配置，不应直接复用导出文件中的真实值。
7. **执行提交及运行验证。** 先补齐缺失数据源，再测试节点提交、试运行和依赖触发。
8. **同步迁移后的变更。** 保存新增、修改、删除任务的清单，验证目标版本与最终源版本匹配。

## 问题与解决方法

### 文件多，但无法判断真实任务数量

文件数量可能包含多个环境、SQL 与配置对、多次导出及辅助文件。应按“项目空间 + 环境 + 任务标识 + 版本”统计；字节去重只能用于存储和资料整理。

### 代码搬过去了，任务仍不能运行

原记录中的未提交节点缺少数据源。需要同步配置与调度依赖，不能仅核对 SQL 文本。

### 导出材料包含客户业务逻辑

SQL 与任务名可能暴露业务规则和内部数据结构。公开文章只保留通用方法，不上传原业务代码、任务清单和配置文件；原文按哈希去重存入私密档案并保留路径对应关系。

## 经验与结果边界

本次对任务材料进行了文本识别、归档、去重和技术主题分类，没有在原 DataWorks 平台重新导入或运行这些任务。拓扑完整性检查属于建议的实施步骤，不能宣称已经通过生产验证。
