异构数据库迁移中，表结构“看起来相似”并不意味着可以直接导入。主键语义、空值、类型和分区设计可能在目标系统中受到不同约束。

## 技术在哪些项目用到

项目 K 保存了大表按时间拆分导出脚本、通过 MaxCompute 外表导入 Hologres 的脚本，以及主键相关报错清单。脚本证明存在相应迁移路径，但不代表所有表导入完成。

## 项目背景

资料呈现了两段链路：部分历史大表按日期范围导出到 MaxCompute；另一段通过外表读取 MaxCompute 数据并写入 Hologres 内部表。不能因为脚本放在同一目录，就断言两段链路已经串联并全部验收。

## 实施步骤

1. **建立表级迁移清单。** 记录源表、数据范围、目标表、字段类型、主键和验证状态。
2. **先检查主键。** 对候选单列或联合键检查 NULL 和重复值，确认业务唯一性。
3. **按源数据类型定义外表。** 原脚本特别提醒外表字段类型应与 MaxCompute 保持一致，而不是照搬另一个源数据库的类型。
4. **独立设计目标内部表。** 对照目标版本能力处理字段、主键、分布及分区，不宜简单删除不兼容 DDL 就认为适配完成。
5. **按时间分批处理大表。** 原脚本按年或月提取日期范围。建议保存分批清单、源行数、目标行数和重试状态。
6. **明确字段映射并导入。** 外表读取与内部表写入应使用明确列名，减少字段顺序变化带来的错误。
7. **恢复必要的注释和业务元数据。** 原文另有生成注释脚本，说明元数据处理属于独立步骤。
8. **执行一致性核验。** 检查表级和分批行数、主键唯一性、空值以及关键业务聚合。

## 问题与解决方法

### 候选主键包含 NULL

报错清单记录了 `null value ... violates not-null constraint`。应统计空值并回到业务定义判断字段是否适合作为键，再决定修复数据或重新设计键。原资料未记录最终处理结果，不应宣称已清理完成。

### 浮点列不能作为主索引键

原记录出现了 float／double 类型不能作为 primary index key 的报错。应按目标版本核查主键支持类型，优先选稳定的业务标识。[Hologres 主键文档](https://help.aliyun.com/en/hologres/user-guide/primary-key)直接把浮点数转换为整数或字符串可能改变唯一性，需要先验证。

### 批处理脚本存在可执行性风险

原大表脚本中能看到赋值格式、变量引用与日期筛选列不一致等问题；外表脚本还包含清空工作目录和按文本行提取 DDL 的操作。本文提炼流程，没有把这些脚本作为已验证工具交付。正式复用需要逐表检查输出 SQL，再在演练环境验证。

## 经验与结果边界

主键报错是明确的失败证据，解决措施是整理后的建议。资料缺少修复后重新导入及最终校验记录，因此本篇属于迁移设计与问题分析。
